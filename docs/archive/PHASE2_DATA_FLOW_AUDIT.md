# 二期数据流与数据库检查（2026-10-08）

> 本文是整改前的检查记录。以下问题已在本轮落实整改，当前实现、验证结果和操作说明见 [PHASE2_HARDENING_RESULT.md](PHASE2_HARDENING_RESULT.md)，性能建议见 [PHASE2_PERFORMANCE.md](PHASE2_PERFORMANCE.md)。

结论：可继续本地开发联调，尚不能按正式运营的异常恢复能力验收。本轮不更改现有业务顺序；当前代码是开发付款后自动完成定妆照和视频。

## 数据经过哪些地方

| 环节 | 保存内容与位置 | 已有约束 |
| --- | --- | --- |
| 选模板、建立草稿 | SQLite projects：模板版本、角色坑位、参与模式 | 重复请求复用草稿；同一请求不能换成其他模板 |
| 上传照片 | 本机上传卷保存图片，projects 保存所属角色、照片地址和检查状态 | 上传前后均检查订单状态；开始制作后不能改角色 |
| 一人体验 | projects 保存游客选择的角色，其余角色读取对应模板人物素材 | 不自动复制游客人脸；未参与角色的草稿照片不进入生成请求 |
| 开发付款 | projects 保存唯一订单号、模板运行快照和零元付款记录 | 数据库事务防重复下单；真实环境禁止开发跳过付款 |
| 定妆照制作 | Redis 保存下游制作任务；完成后 SQLite 保存角色对应表 | 角色编号必须匹配模板；返回资料不完整则不进入视频制作 |
| 定妆照归档 | TOS 保存图片，SQLite 保存作品照片地址和资产编号 | 存储失败只重试保存；重复完成通知不会把视频阶段回退 |
| 视频制作 | MySQL video_tasks 保存任务和角色对应表，Redis 作缓存 | 使用游客原图／模板人物、造型参考和场景图；不传展示用定妆照 |
| 作品完成 | 合成配乐、存入 TOS，SQLite 保存作品地址和完成消息 | 已完成视频不被后续结果覆盖；不发放抽奖机会 |

SQLite 位于本地 Docker 上传数据卷，不在浏览器或微信开发者工具缓存中。MySQL、Redis 也使用独立本地卷。不要通过删除卷来更新服务。

## 仍需整改（按优先级）

| 优先级 | 发现的问题 | 影响 | 整改方案 |
| --- | --- | --- | --- |
| 最高 | 视频模型成功后，合成或上传失败仍进入整个视频任务重试 | 可能再次生成并重复产生模型费用 | 保存云端任务编号、云端结果、当前处理步骤；合成和上传分别恢复，只在云端明确生成失败时重新生成 |
| 最高 | 云端视频任务编号只保留在工作进程和日志，没有数据库恢复记录 | 工作进程退出后可能一直显示制作中，不能续查原云端任务 | 提交前记录请求状态，响应后立即保存云端编号；后台按编号恢复查询；提交结果未知时进入人工核实，不能盲目重发 |
| 高 | 定妆照制作过程和最新任务索引仍依赖 Redis | 在 SQLite 收到完整结果前丢失 Redis，会失去恢复依据 | 为定妆照任务、角色中间产物及最新任务关系建立持久记录，Redis 仅作缓存 |
| 高 | 视频读取优先信任 Redis，最新任务查询和创建也依赖 Redis 索引 | 数据库已更新但缓存更新失败时可能显示旧状态；索引丢失会妨碍核对原任务 | 以数据库任务和运行编号为准，缓存失效回查数据库，数据库约束同次制作不能重复建任务 |
| 高 | 使用 local-user 开发身份 | 不能隔离不同真实用户的作品 | 上测试服务器供多人使用前接入微信登录，所有作品、照片、消息接口校验归属；付款继续按当前约定保留待接 |
| 中 | SQLite 项目内容整体保存在 JSON 中，后台反复扫描全部作品 | 作品多时查询成本增大；不适合多台应用服务器各存一份 SQLite | 后续集中到 MySQL，分开作品、订单、角色照片、任务、素材和消息，按状态及下次检查时间查询待处理任务 |
| 中 | 尚未完成备份恢复演练；临时隧道地址可能改变 | 数据卷损坏或地址变化会影响恢复及旧素材访问 | 备份数据库与资产记录并实际还原一次；素材保存文件编号和存储位置，访问地址按当前配置生成 |
