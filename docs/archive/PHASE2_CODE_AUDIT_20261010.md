# 二期前后端、数据流与数据库检查报告

检查日期：2026-10-10。对象：本地当前代码，目录 `G:\桂智旅\aitravel\aitravel`。

本次完成代码审查及部分离线验证，未修改业务代码，未部署、连接服务器数据库或调用收费云服务。服务器实际表结构、在线负载及已部署代码版本仍需在测试服务器核实。本报告描述代码事实与整改建议，不代表这些整改已经实施。

## 1. 结论与最新业务规则

二期主要业务已经独立出来，不需要为了清理一期再推倒重写。但存在定妆照失败重试接口不匹配、同一张模板表存在两套建表定义、长任务占住执行位置等问题，应先修复这些，再扩大模板量和用户测试规模。

以用户最新要求为准：**定妆照生成并保存后，自动进入视频生成，不再要求用户确认下一步。**

当前 `server/phase2/store.py:106` 的 `portrait_saved()` 已实现：保存定妆照资料后，将项目改为 `video_submit`。`server/phase2/orchestrator.py:132` 也要求定妆照已保存才提交视频。重复保存回执不会让已进入视频阶段的项目倒退。

这里的“自动”是保存成功后进入后台队列；遇到排队、服务故障或云端限流，不能保证视频模型在同一秒开始工作。前端应明确显示“定妆照已完成，视频排队中／生成中”。

仍保留以下规则：

- 首页直接上下刷竖屏模板，景区和其他条件在页面内筛选。
- 按模板角色分配上传位置，支持一人体验，不额外设“主角”。
- 定妆照是展示和保存的用户资产，不作为视频模型的参考图片。
- 最终定妆照和视频为竖屏；内部人物三视图是中间材料，其横向排版不等于最终作品横屏。
- 付款仍是开发环境跳过，不能视为已完成正式收款功能。
- 模板导入成功后默认上架，展示热度默认基数 10000；真实选择记录独立保存。

## 2. 当前实际数据路线

| 顺序 | 发生什么 | 主要数据与去向 |
|---|---|---|
| 1 | 游客浏览、筛选模板 | 主服务读取已上架模板，返回名称、介绍、角色、封面和示例视频 |
| 2 | 选择拍同款 | 创建草稿，保存当时模板内容，避免模板后来被修改影响已有作品 |
| 3 | 选择参与方式、上传角色照片 | 上传位置来自模板角色；一人体验只替换所选角色，其余使用模板人物 |
| 4 | 检查照片 | 原图保存在主节点上传目录，后台调用人脸检查并记录结果 |
| 5 | 创建订单、跳过开发付款 | 建立订单与项目关联，进入定妆照制作 |
| 6 | 生成定妆照 | 为参与游客生成内部三视图，再生成最终竖屏定妆照 |
| 7 | 保存定妆照 | 保存到对象存储，记录资产编号和引用；成功后自动切到视频阶段 |
| 8 | 提交视频 | 使用游客原始人脸照片、人物三视图和模板场景参考；不使用最终定妆照，不走分镜图生成 |
| 9 | 等待视频制作 | 将所需参考素材登记到视频素材库，等待可用，提交视频模型并查询结果 |
| 10 | 保存成片 | 按当前代码处理背景音乐、保存到对象存储，更新项目为完成 |
| 11 | 用户查看作品 | 后端校验作品归属，返回临时访问地址；“我的作品”展示进度及成果 |

已有的保护值得保留：提交前先记录状态、请求结果不明时先查询原任务、任务记录可恢复、作品归属检查、私有素材临时地址、模板版本目录，以及对象存储和生成服务分开的密钥配置。

## 3. 已确认问题与整改建议

### A. 优先修复：定妆照失败重试地址不匹配

证据：`server/phase2/orchestrator.py:135` 请求 `/api/v1/image/task/character/<task_id>/retry`，但 `server/common/durable_generation.py:180` 注册的是 `/api/v1/image/task/<task_id>/retry`。

离线接口验证：前者返回 **404**，实际注册地址返回 **202**。验证中已替换真正的任务启动方法，没有生成图片或调用云端。

影响：首次生成可以成功，但定妆照失败后的重试会落到不存在的接口，项目可能反复显示查询或恢复原任务。

建议：统一调用地址；增加从主服务发起失败重试到生成服务接收的接口测试，覆盖重复点击及请求超时。仅测单个服务内部方法不能发现这种跨服务地址错误。

### B. 优先修复：模板表定义由启动顺序决定

证据：

| 定义位置 | 模板内容字段 | 上架默认值 | 其他差异 |
|---|---|---|---|
| `server/admin/store.py:15` | `payload_json TEXT` | 0 | 未定义另一版本中的创建、更新时间及筛选索引 |
| `server/phase2/phase2_app.py:119` | `payload_json JSON` | 1 | 定义时间字段及景区、类别、人数索引 |

两处都是“表不存在才创建”，后启动的服务不会把已有表自动改成自己的定义。因此，部署顺序会影响真实结构。之前数据节点先启动，但本次没有查看服务器，不能直接断言服务器现在是哪套结构。

另外，`server/common/task_journal.py:32` 中任务内容字段也是 `TEXT`。MySQL 的该类型容量约 64 KB，长提示词、模板内容、素材地址和过程记录累计后存在超限风险；本地 SQLite 测试不能验证这个限制。

建议：采用一份正式表结构和版本升级脚本；先检查实际字段，再备份并升级。模板及任务大内容按需要使用 JSON 或 LONGTEXT，并在上传时检查大小。两个应用启动时只检查结构版本，不分别猜测建表。不要通过删库重建解决。

### C. 主要性能瓶颈：等待云端结果占住执行位置

证据：`infra/staging/docker-compose.ai.yml` 的定妆照和视频服务均配置 `PHASE2_GENERATION_WORKERS: '1'`。`server/common/durable_generation.py` 的一个任务会经历素材准备、云端提交、轮询、成片处理和保存；`server/common/video_provider.py:228` 的等待可持续较长时间，期间执行位置不释放。

影响：当前每个视频服务进程基本一次处理一条完整视频管线。云端允许并发，并不意味着本地会充分利用。后续订单会排队；单纯增加前端刷新频率毫无帮助。

主调度器也只有两个工作位置；同步人脸检查的读取等待上限为 180 秒。照片检查变慢时会拖累其他项目状态推进。

建议：把“提交任务”“到时间查询一次”“保存结果”拆开；等待云端期间只保留下一次查询时间，释放执行位置。照片检查分开排队，再根据供应商额度设置并发上限。增加队列长度、最久等待时间、制作耗时、错误比例监控，不能直接无上限加线程。

### D. 模板允许上传的内容，比生成时实际使用的范围更大

证据：`server/phase2/runtime_templates.py` 接受并检查多个提示词组，但 `server/common/template_client.py:19` 只读取第一个组的 `Prompt`。`server/common/video_provider.py:30` 的视频时长固定为 15 秒。

影响：多组提示词可以通过导入，后续组却不参与生成；如果模板标注其他时长，会与实际模型请求不一致。不能据此断言现有每个模板都受影响，但后续批量上传会放大这种风险。

建议：当前阶段明确只支持一个视频提示词组和 15 秒，并在导入时指出具体冲突文件。若要支持其他配置，应一起修改模板规范、模型请求和前端展示。保存每次实际使用的生成参数，方便以后定位作品为什么不符合预期。

当前有背景音乐素材时会混入成片，同时视频模型也启用了音频生成。应明确人声、环境声、模型音乐与模板音乐如何处理，避免叠音；这属于需要统一的产品规则。

### E. 前端列表和刷新策略有增长性问题

| 位置 | 当前行为 | 影响 | 建议 |
|---|---|---|---|
| `client/pages/phase2/entry/entry.js`、对应 WXML | 后续模板不断追加，再整体更新列表；只创建当前播放视频，但封面和滑动项持续累计 | 刷到数百条时页面节点与更新量增长 | 页面只保留附近 3～5 个实际滑动项；模板资料单独缓存；按需加载缩略图 |
| `client/pages/phase2/upload/upload.js` | 约每 2.5 秒查询项目 | 没上传或照片已全部通过时仍产生请求 | 仅在检查状态变化期间查询，页面隐藏即停止 |
| `client/pages/phase2/work/work.js` | 约每 5 秒查询，并重复提交已读 | 增加无必要读写 | 状态变化再标已读；等待时间长时降低查询频率 |
| `client/pages/phase2/works/works.js` | 未完成作品时定时回到首批 30 条；追加分页时又会清除计时器 | 已加载后页可能被替换；追加后进度可能不再自动更新 | 保留分页顺序，按已加载作品编号更新状态，独立管理刷新计时器 |
| 已完成作品媒体 | 临时地址约一小时失效，完成后停止轮询，媒体失败只提示 | 长时间停留后可能不能重播或加载 | 媒体加载失败时刷新一次访问地址，不重新生成作品 |

这些是代码层面的风险和行为判断，尚未在不同机型上测量内存、帧率或首次加载时间。

### F. 列表查询和项目保存做了较多重复工作

- `server/phase2/phase2_app.py:98` 周期性新建数据库连接、读取全部已上架模板并解析，目录缓存刷新在共用锁内完成；连接未显式设置连接和读写超时。
- 游客目录与管理列表读取热度时会读取全部设置并汇总真实选择记录。用户量增长后，其成本不只取决于当前返回的十几条模板。
- `server/phase2/mysql_store.py:91` 保存一个项目时，会写整个项目内容，并遍历更新角色、订单、资产，即使只改了一次查询时间。

建议：复用有超时限制的数据库连接，预先整理游客端需要的简短模板资料；热度只查询本页模板，或维护可核对的汇总值；任务时间、状态等使用小范围更新，避免每次重写全部内容。必须保留同一项目更新的一致性和防重复保护。

离线模拟仅测目录筛选和排序的 CPU 时间，30 次运行结果如下：

| 模板数量 | 平均耗时 | 本次最大耗时 |
|---|---:|---:|
| 500 | 4.044 毫秒 | 4.280 毫秒 |
| 1000 | 8.073 毫秒 | 8.183 毫秒 |

这不是服务器接口压测，不包含数据库、网络、图片或视频。结果表明：目前不能把“500 个模板本身”认定为最大瓶颈，应优先处理媒体加载、数据库重复操作和生成排队。

### G. 素材分布在多处，备份和清理尚不完整

| 内容 | 当前主要位置 |
|---|---|
| 游客上传原图 | 主节点 `phase2_api_uploads` 数据卷 |
| 人物三视图等中间文件 | 数据节点 `phase2_uploads` 数据卷 |
| 管理员导入模板 | 数据节点 `phase2_templates` 数据卷 |
| 视频合成中间文件 | AI 节点 `phase2_results` 数据卷 |
| 最终作品 | 私有 TOS 对象存储 |
| 对象与访问资料的映射 | 数据节点 `phase2_tos` 中的本地 JSON 文件 |

`server/local/tos_app.py` 读取对象时依赖本地映射。只保留对象存储内容，不备份这份映射，不能保证应用恢复后还能访问已有作品。

未发现覆盖所有中间材料、孤立上传和过期作品的完整自动清理流程。现有本地备份脚本不能直接视为三节点部署的完整恢复方案。

建议：在数据库中登记文件的存储桶、对象路径、类别、大小、来源和保留期限；统一备份数据库及必要数据卷，并做一次恢复演练。旧模板版本可能仍被历史项目引用，应按引用清理，不能按日期直接删除所有旧目录。

### H. 公开模板展示和内部生成资料的边界不够明确

`server/phase2/auth.py` 放行普通模板路由，常规模板的运行资料接口可返回生成提示词及参考地址；项目快照另有保护，不能混为一谈。

`server/phase2/phase2_app.py` 的模板静态文件路由按目录发送文件，没有按封面、示例视频等用途限制允许的文件类型。发布工具还会把整个测试模板目录打进主节点包，排除规则不包含 `.rar`。因此工作目录里的模板源文件和额外压缩包可能随包分发，并存在通过已知静态路径访问的风险。本次没有在线验证文件暴露。

建议：游客接口仅返回展示需要的资料；生成提示词和内部参考资料通过内部认证读取。发布时按清单收集资源，模板通过管理端导入，避免将本地测试工作目录整体作为公开素材目录。

### I. 批量模板上传还需要加强内容检查和去重

现有导入会检查图片可读取，但视频主要检查文件头，未完整验证视频是否能解码、实际时长、竖屏比例和兼容格式。部分角色或场景素材按文件名前缀识别，格式限制不够完整。基础资料中的部分类型与长度也缺少严格约束。

管理员上传后默认上架是既定要求，应在上架前把内容检查完成，否则单条坏模板可能影响游客浏览或生成。

此外，相同景区、相同名称的检查主要在应用中完成，数据库没有相应唯一限制；并发上传存在重复导入窗口。批处理中的文件名识别也不等于内容一致性检查。

建议：上传返回逐模板、逐文件的错误列表；验证视频可播放及尺寸；校验元数据类型、角色编号及对应素材是否一一匹配；通过事务和唯一业务标识处理重复，明确“更新已有模板”与“新增模板”。不要仅凭压缩包文件名判断内容相同。

## 4. 真实数据库结构与字段建议

以下基于当前 MySQL 建表代码，不是旧设计文档中设想的表，也不代表已经读取服务器确认。

| 表 | 存什么 | 当前主要字段含义 | 问题或建议 |
|---|---|---|---|
| `phase2_templates` | 模板目录 | 编号、景区、类别、人数、上架状态、排序、完整模板内容 | 两套定义必须统一；业务筛选字段与完整内容应保持一致 |
| `phase2_template_settings` | 展示设置 | 模板编号、热度基数、是否显示热度、版本号 | 基数与真实人数分开是合理的；补充修改时间便于核查 |

| `phase2_projects` | 一次制作的总记录 | 项目编号、用户、阶段、是否待处理、下次处理时间、订单号、完整项目内容 | 调度有索引；减少大内容重复写入，明确结构化字段与完整内容哪个为准 |

| `phase2_assets` | 用户资产索引 | 资产编号、项目编号、类别、引用地址 | 信息偏少；增加存储位置、大小、格式、宽高、来源、状态和时间；视频任务编号与作品资产编号应各有含义 |
| `phase2_tasks` | 下游生成任务 | 任务号、类别、运行编号、状态、下次执行时间、完整任务内容 | 有防重复约束和调度索引；内容 TEXT 容量及等待占槽问题要处理 |
| `phase2_events` | 用户可见进度通知 | 事件号、项目编号、类别、标题、时间、是否已读 | 已有项目关联；不要每轮前端查询都重复写已读 |
| `phase2_task_events` | 任务运行日志 | 事件号、任务号、类别、状态、消息、时间 | 需日志保留和清理周期；按任务查看日志时检查索引是否匹配查询 |
| `phase2_leases` | 避免多个进程同时处理同一项目 | 项目或锁编号、处理者、到期时间 | 属于二期运行保护，不是可删除旧表 |
| `phase2_admin_audit` | 管理操作记录 | 操作者、动作、对象、详情、时间 | 建议保留，但对详情内容做脱敏及长度限制 |
| `phase2_admin_attempts` | 管理登录尝试 | 来源、时间 | 保留限流用途，定期清理历史记录 |
| `phase2_migrations` | 数据迁移记录 | 迁移名称、执行时间 | 已有迁移记录不等于模板表已具备统一结构升级流程 |

通用建议：金额明确用“分”，时间统一含义与时区约定；长期资产保存稳定的存储引用，不保存临时签名地址作为唯一凭据；关键状态的允许值需要约束；修改表结构前必须做兼容现有记录的升级与回退设计。

当前 `PHASE2_DATA_MODEL.md` 含有旧交互及尚未实施的表设计，不能直接当作真实数据库说明。后续应以统一升级脚本和实际字段清单更新该文档。

## 6. 需要统一口径的业务事项

| 事项 | 当前实际行为 | 建议口径 |
|---|---|---|
| 定妆照后是否等用户确认 | 保存后自动进入视频 | 按最新要求保留，前端只展示，不再拦截下一步 |
| 热度默认一万人 | 显示基数 10000 加真实选择人数 | 管理端分别展示“展示基数”和“真实选择人数”，避免把两者相加当经营数据 |
| 什么叫真实选择 | 创建订单时按用户与模板去重记一次 | 不称为付款人数或制作成功人数；全站人数需另算 |
| 替换模板后的热度 | 基数重设为 10000、显示开启，已有真实记录保留 | 明确属于同一模板的更新还是新作品模板，防止错误继承或重置 |
| 热门排序 | 当前目录采用带种子的打散排序，不是按热度排名 | 如果页面叫“热门”，要确定是运营推荐还是实际热度排行 |
| 一人体验 | 只替换选中的游客角色，其余模板人物保留 | 上传位置和最终角色对应关系必须一致，不再添加主角概念 |
| 视频时长、多提示词组 | 固定 15 秒，只用第一个组 | 当前先限制输入并给出清晰错误；扩展时一起升级生成和展示 |
| 数据保留 | 最终资产与中间文件分散存储，缺少统一期限 | 最终作品、中间图、上传原图分别定义保留周期，并考虑用户删除后的处理 |

## 7. 建议整改顺序及验收

1. **先修可复现功能错误**：统一定妆照重试接口；验证首次失败、重试成功、重复重试不重复计费，以及定妆照保存后自动接续视频。
2. **统一数据库结构**：读取测试库实际结构，备份，再通过一次正式升级修复模板表差异及大内容容量。验收先启动管理服务、先启动主服务均得到相同结构。
3. **收紧模板导入及公开资料**：导入时验证格式、角色素材、视频尺寸和时长；明确多组提示词策略；剔除发布包中的源压缩包；内部资料加访问保护。
4. **修任务调度和前端刷新**：云端等待不占执行位置；人脸检查单独排队；稳定分页和媒体过期刷新；滑动页面限制实际渲染项数量。
5. **完善资产与恢复方案**：补充资产存储字段、备份必要数据、测试恢复旧作品；之后才启用按引用关系清理中间文件。
6. **最后做服务器实测**：导入至少 500 条有效模板，测浏览延迟、真机播放及连续滑动内存；生成部分从少量真实任务起步，观察排队及配额，再决定并发上限。收费测试另行执行，本轮没有进行。
