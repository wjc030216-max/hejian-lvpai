# 二期性能建议（2026-10-08）

## 本轮已做

| 改动 | 作用 |
| --- | --- |
| 待处理任务建立状态与时间索引 | 不用每三秒读取全部作品 |
| 订单、角色、素材、消息分表 | 查询用户作品和定位照片不用扫描目录或整批记录 |
| MySQL 复用连接 | 减少频繁连接数据库 |
| 模板列表缓存 15 秒 | 减少重复查询；修改后最迟 15 秒刷新 |
| 作品每页 30 条，增加查看更多 | 避免一次拉取所有历史作品 |
| 全部作品已结束时停止列表定时刷新 | 减少无意义请求，重新进入页面仍刷新 |
| 本地默认每个生成服务并发 2 个任务；三机测试部署定妆照、视频各 1 个 | 适应 AI 节点 2 核 8 GB，避免网络和云端配额瞬间被占满 |
| 每步保存生成结果 | 故障恢复跳过已成功步骤，减少等待及重复费用 |

## 当前测量

本机 3 个真实测试模板，每个读取接口预热一次后连续请求 30 次，无并发、无云端生成。

| 接口 | 一半请求耗时不超过 | 95% 请求耗时不超过 |
| --- | --- | --- |
| 模板列表（每页 8 条） | 4.5 毫秒 | 27.1 毫秒 |
| 作品列表（每页 30 条） | 5.1 毫秒 | 19.3 毫秒 |
| 未读消息 | 3.5 毫秒 | 26.5 毫秒 |

这不是 500 多模板、多游客或云端生成的容量测试，不能据此承诺线上承载人数。

## 建议顺序

| 优先级 | 建议 | 理由 |
| --- | --- | --- |
| 第一 | 导入全部真实模板后，分档测试 10、30、50 位游客同时浏览 | 分别记录接口、视频首帧和上传耗时，找到瓶颈后再加配置 |
| 第一 | 样片准备适合手机的预览版，封面压缩；只加载当前及相邻两条视频 | 大量模板的首屏等待往往来自视频下载，不要预加载全部样片 |
| 第一 | 素材使用对象存储配合内容分发，正式测试用固定素材域名 | 临时隧道适合本地联调，不适合长期承担游客视频流量 |
| 第一 | 分别统计图片生成、视频生成、合成、上传耗时和失败次数 | 云端模型慢与本机存储慢要分别处理；增加本机 CPU 不会直接加快云端模型 |
| 第二 | 三机部署先保持定妆照、视频各并发 1，再结合云端额度、排队时间和内存逐步增加 | 不要直接开几十个任务；遇到限流先等待，不要高速重发 |
| 第二 | 多机部署时把后台制作进程独立出来 | 当前单机使用持久任务加后台线程，独立进程更便于扩容和控制资源 |
| 第二 | 上传照片压缩前先验证人脸检测通过率 | 确保不影响识别和生成质量，再减少体积 |
| 第二 | 作品很多后改成按最后一条作品编号向后查询 | 避免深页码不断增长后跳过大量前页记录 |
| 第三 | 中间素材先对账再定期清理 | 不删除仍在制作或被作品引用的文件 |
| 第三 | 备份复制到另一块盘并定期恢复验证 | 同盘备份不能防整盘损坏 |

数据库无需因为 500 多个模板就拆成多台。先根据实际同时使用人数、云端配额和素材流量决定机器数量。
